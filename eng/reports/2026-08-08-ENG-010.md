## Problem

iOS Safari drops `keepalive` fetch POSTs when a user taps an `sms:` link (the scheme-handler navigation kills the tab before the beacon sends). ~40% of real landing traffic (iOS/iPhone/Safari) produced zero `sms_tap` events. ENG-009 diagnosed this; ENG-010 is the fix.

---

## What shipped

### `/go/{code}` route rewritten (`landing.py`)

Old: 2-line redirect to `/?c=<code>` (302 → landing page).

New:
1. Validates code against `_CODE_RX`
2. Records `sms_tap` in `hal_funnel_events` via `_record_tap()` (background task — fires before any redirect)
3. Returns `Cache-Control: no-store` HTML with three navigation layers:
   - `<meta http-equiv="refresh" content="0;url=sms:...">` — most reliable on iOS
   - `window.location.replace('sms:...')` — JS fallback
   - Visible "Tap to open Messages" button — final fallback
4. HTTP 302 to `sms:` explicitly avoided (blocked by iOS since iOS 8)
5. `utm_source`, `utm_medium`, `utm_campaign` accepted as query params; stored in event row; `utm_source=verify-test` is excludable from funnel dashboards

### `render_landing()` sms_href change (`landing.py`)

When `code` and `number` are both truthy:
```python
sms_href = f"/go/{code}"   # was: f"sms:{sms}&body=..."
```

All four CTA locations (hero, sticky, nav, closing) now route attributed traffic through the server-side tap endpoint. Organic visitors (no code) keep direct `sms:` links unchanged.

### UTM forwarding JS (`_TAP_BEACON_JS` in `landing.py`)

Added a JS block that reads UTM params from `window.location.search` and appends them to any `a[href^="/go/"]` hrefs before navigation. This ensures UTM metadata reaches the `/go/` endpoint even though it's not embedded in the static href.

### No changes needed to `metrics.py` / `device_traffic.py`

Both scripts query `hal_funnel_events WHERE event_type='sms_tap'`. The new server-side events use `event_type='sms_tap'` — they are automatically counted by all existing queries.
