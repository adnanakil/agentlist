## Diagnosis

### 2026-08-06 g1 conversion — what happened

The user was on mobile. They activated the `sms:` link (which encoded
`?c=g1` in the `body=` prefill). Their Messages app received the prefill text —
confirming the link formed correctly — and they sent the message, which is how
`acquisition_source='g1'` reached HAL. iOS Safari then dropped the keepalive
POST /tap when it yielded to the scheme-handler navigation.

**The desktop copy-to-clipboard path is ruled out.** The `.copy-num` button
copies only the bare phone number — the `(g1)` attribution code lives inside
the `sms:` URI's `body=` parameter and never reaches the clipboard. A desktop
user would have had to manually type the full prefill including `(g1)`, which is
not a plausible user path.

The `hal_page_hits` table should have a row for 2026-08-06 with
`attribution_code='g1'`. That row is the server-side proof of the visit — it was
written before the browser ran any JS. Adnan or growth can confirm with:

```sql
SELECT * FROM hal_page_hits
WHERE attribution_code = 'g1' AND is_bot = false
ORDER BY created_at;
```

### Why the beacon was silent

iOS Safari drops keepalive XHR/fetch requests when a click handler triggers
`sms:` (or any scheme-handler) navigation. This is documented iOS behavior.
The `keepalive:true` flag is the correct approach on every other platform
and on desktop; iOS is the exception. The result: a real mobile conversion
produces a tap in Messages but 0 rows in `hal_funnel_events`.

## What shipped

### JS changes (`_TAP_BEACON_JS` in landing.py)

1. `tap()` → `tap(evType)`: function now accepts an event-type string and
   includes `event_type` in the POST body.
2. `sms:` link click listeners now call `tap('sms_tap')` explicitly (no
   behavior change — same payload, same endpoint, now labeled).
3. `.copy-num` click handler now calls `tap('sms_copy')` **before** the
   clipboard write. Fires regardless of clipboard API availability — intent
   is captured even when clipboard fails.

### Server changes (landing.py)

- `_ALLOWED_EVENT_TYPES = {"sms_tap", "sms_copy"}` constant
- `_record_tap` accepts `event_type: str = "sms_tap"`; deduplicates per
  `(visitor_hash, event_type)` so one visitor can emit both in 60 seconds
- `/tap` endpoint validates `event_type` against the whitelist; unknown
  values default to `"sms_tap"` — no invented buckets from hand-crafted POSTs

No migration. `HalFunnelEvent.event_type` is `String(64)`, free-form.

## Server-side cross-check (measurement path without browser dependency)

`hal_page_hits.attribution_code` is written server-side on every `GET /`
that carries `?c=`. No JS required. Cross-reference query:

```sql
-- Server-side: arrived with a code (no JS dependency)
SELECT attribution_code, COUNT(*) AS views, MIN(created_at) AS first_seen
FROM hal_page_hits
WHERE is_bot = false AND attribution_code IS NOT NULL
GROUP BY attribution_code ORDER BY first_seen;

-- Beacon-side: tapped or copied (lossy on iOS for sms_tap)
SELECT attribution_code, event_type, COUNT(*) AS events
FROM hal_funnel_events
WHERE utm_source != 'verify-test'
GROUP BY attribution_code, event_type ORDER BY attribution_code, event_type;
```

The gap between `views` and `events` for the same code is the beacon miss rate.
For g1: expect 1 row in `hal_page_hits` and 0 rows in `hal_funnel_events` —
confirming the beacon was dropped, not that the user lacked intent.

## EXP-006 and EXP-011 trustworthiness

**EXP-006 LOSS: cannot be trusted.** At least one confirmed conversion (g1,
2026-08-06) produced zero tap events. The 0-tap reading that drove the LOSS
was instrument failure, not behaviour. The experiment data cannot be re-derived —
the beacon was the only intended record, and it was lossy on the majority mobile
platform.

**EXP-011 in-flight: treat the tap count as a lower bound, not a true rate.**
- Desktop copy (`sms_copy`) is now instrumented — future desktop conversions
  will be captured.
- The iOS `sms_tap` keepalive drop is not fixed here — it is a platform
  limitation. Mobile tap counts remain under-counted for iOS visitors.
- `hal_page_hits` (post-bot-fix view count) is the more reliable reach
  numerator. Tap + copy events are the conversion lower bound.
- Growth should not call EXP-011 a LOSS on tap count alone. Recommended gate:
  `(sms_tap + sms_copy events) / (non-bot page views)` with the caveat that
  the iOS mobile fraction of the numerator is still under-counted.

## Residual gap (not addressed by this ticket)

iOS keepalive drop on `sms:` navigation cannot be fixed by tuning the beacon.
The clean fix would route mobile clicks through a server-side redirect:

- `/go/{code}` already exists and redirects to `/?c=code` (302)
- If it redirected to the `sms:` URI directly (after recording a page-hit),
  the intent would be recorded server-side before the browser yields to the
  scheme handler
- This changes the click path and needs its own ticket + review
